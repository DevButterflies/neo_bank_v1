Complete REST surface of the composed platform: Bank Orchestrator v3.4.0

How to read this playbook
  • Base URL — every path is relative to http://localhost:8000. All five services are mounted in one process.
  • Wire format — flat JSON everywhere: enums arrive as plain strings ("TRACK_1_CLASSICAL"), datetimes as ISO-8601 strings. No internal persistence markers.
  • Errors — uniform body {"detail": "..."}. Semantics: 404 unknown identifier, 409 prudential veto / state-machine conflict / governance PENDING, 422 validation gate (unconfirmed packet, amounts outside outstanding, out-of-scope product).
  • Auth — none (demo deployment; CORS is open).
  • Reading order for a demo — create a candidate in Pillar 1 → submit (Pillar 2 scores it) → approve → disburse; then watch Pillar 3 facilities/postings/ledger and Pillar 4 buffer balances / capital snapshot / veto state update.
  • Veto semantics — GET /p4/veto/consult is the state Pillar 2 must consult before confirming a packet. Pillar 3 never sees a veto event; it only ever sees a confirmed packet or none.
  • Per-service docs — each sub-app also serves its own Swagger at /p1/docs, /p2/docs, /p3/docs, /p4/docs, /governance/docs.

PUT/bilan/config
Update bilan config
operationId: put_bilan_config_bilan_config_put · tags: bilan

Merge a partial update into bilan_config_v1 and return the result. This is the only bilan path that writes — to a brand-new KV key, leaving p3_state_v1/p4_state_v1 (and therefore /ready) untouched. Requires X-Admin-Token and leaves an append-only audit row behind. The config write and the audit append are two separate KV writes and are not atomic: the config is committed first, then the audit row. If the audit append fails the error is logged and the response is still 200, because the caller's change *did* take effect — reporting failure would invite a retry that then records a spurious second change. A failure of the config write itself still propagates (no transaction layer is built here; see bug_bilan_fix_round_2.md, R4).
